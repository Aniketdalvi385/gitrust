UX critique · agentic CLI

GiTrust reads its own intent out loud,
then forgets it's an agent.

The flows you described are 80% there — safety tiers, recovery snapshots, plan previews, type-to-confirm. The polish gap is mostly in tone, default behavior, and consistency. Below: what's already working, six cross-cutting fixes, then concrete before/after rewrites for each flow. Everything quoted as "what to change to what."

Things you should not touch

After seeing the full loop (status → branch list → commit → conflict check), it's clear the foundation is stronger than the screenshot let on. Flagging these so they don't get redesigned out by accident.

Keep · Typo tolerance

gitrust 'statsus' just works

Quietly running status when the user fat-fingers it is exactly the delight an agentic CLI should provide. Don't add a "did you mean…" prompt — silent rescue is better than chatty rescue.

On branch main · tracking origin/main · 1 ahead · 1 behind is denser and more scannable than git status's 4-line preamble. The middot separator + concrete ahead/behind counts are doing real work.

Keep · Branch list

Branch table is information-dense

* main → origin/main (↑1 ↓1) packs current/upstream/ahead-behind into one line. The master (no upstream) annotation on the sibling row is the kind of detail that saves a beginner from a 20-minute debugging session.

Keep · SHA transitions

(aa44620 → 0de4a0d) in commit confirmation

Showing the SHA delta after a write op is the kind of receipt that gives power users confidence and gives beginners a thing to copy when something goes wrong. Use this pattern on every write op (push: origin/main 0de4a0d → 1a3f4b8).

Keep · Generated commit msg

Drafting commit message before the plan box

The order — generate message, show it editable, then show the plan that uses it — means by the time the user is at "Execute? [Y/n]" they've already approved the wording. Compare to tools that bury the editable message inside the plan box. Don't change this sequence.

Six things I'd change everywhere

01 · Identity

Stop dropping into raw git mid-flow

In the screenshot, option 1 is gitrust "pull" but options 2–4 are raw git. That's an identity crisis — users came to GiTrust precisely so they wouldn't have to remember --force-with-lease.

2. Rebase:      git pull --rebase
3. Keep yours:  git push --force-with-lease  ⚠⚠
4. Discard yours: git fetch && git reset --hard origin/<branch>
2. Rebase       gitrust "rebase onto origin"
3. Force push   gitrust "force push"      ⚠⚠
4. Discard mine gitrust "discard my commits"  ⚠⚠
02 · Confidence

Stop hedging once you've fetched

You already ran git fetch. You know. "Predicted" makes it sound like the LLM guessed, which undermines trust in the safer messages that should sound certain.

⚠ Merge conflicts predicted (1 local, 1 remote commit(s) to merge):
⚠ Will conflict on pull · 1 ahead, 1 behind on main
03 · Recommendation

The picker is fine — the wall of text above it isn't

Correction from my first pass: the rich picker does default to Merge. The real problem is everything between the conflict detection and the picker — "Manual fix needed", "Both sides committed…", "Stash will NOT help", and a numbered list that repeats the picker options. By the time the user reaches the picker, they've already mentally branched. Cut the preamble or move it behind ?.

⚠ Will conflict on pull · README.md (~3 lines)
[picker fires immediately — Merge highlighted, [?] for guidance]
04 · Severity

The marker should depend on the branch, not the command

Force-pushing your own feat/login branch is ⚠. Force-pushing main with three collaborators behind it is ⛔. Right now both are flat ⚠⚠. Make GiTrust check git config branch.<name>.remote + protected-branch rules and upgrade the marker dynamically.

force push → origin/feat/login           ⚠   you are the only contributor
force push → origin/main                 ⛔  3 collaborators behind, last
                                              shared push 2 hr ago
05 · Noise

Stop answering questions nobody asked

"Stash will NOT help — it only captures UNCOMMITTED changes" is a paragraph defending against a thing the user didn't propose. If it's truly a common wrong turn, show it on ?. Otherwise cut it. Same for the "Manual fix needed: conflict markers look like <<<..." block — useful once, noise on the 30th time.

Press ? for what conflict resolution looks like
Press why to ask why GiTrust ruled out stash/cherry-pick/...
06 · Recovery

Mention the safety net before the scary choice, not after

Type-to-confirm is good friction, but it's lonely friction if the user doesn't yet know that GiTrust snapshotted the state. Put the recovery promise inline, next to the destructive option. That's what turns "irreversible" into "reversible-with-effort," which is the actual UX you want.

⚠⚠ gitrust "reset --hard HEAD~3"
   loses 3 commits, 99 uncommitted lines
   recoverable for 30 days via:  gitrust undo

Flow rewrites

01Merge-conflict prediction

This is the screenshot. Three things compound: the reasoning leak above the result, the wall-of-text "Manual fix needed" block, and the four-option menu where the default exit is hidden in the prompt line.

Before
$ GITRUST_DEBUG=1 gitrust 'do I have conflicts if I pull changes' (reasoning: User wants to know if there are merge conflicts when pulling changes, so this is a read-only check for merge preview.) Fetching origin… ✓ ⚠ Merge conflicts predicted (1 local, 1 remote commit(s) to merge): • README.md Manual fix needed: Merge/rebase will pause with conflict markers (<<<<<<<, =======, >>>>>>>) inside the affected files. Edit each file to keep the right version, remove the markers, then `git add` it and continue. → Both sides committed conflicting changes. Stash will NOT help — it only captures UNCOMMITTED changes, and you have none. Real options: 1. Merge: gitrust "pull" – produces a merge commit; resolve markers, then commit 2. Rebase: git pull --rebase – replays your commit(s) on top of remote (resolve per commit) 3. Keep yours: git push --force-with-lease ⚠⚠ overwrites remote (only if you're sure) 4. Discard yours: git fetch && git reset --hard origin/<branch> ⚠⚠ loses local commit(s) > Pick a resolution strategy: Do nothing – exit and decide later
After
$ gitrust "do I have conflicts if I pull" dbg → read-only · merge_preview on main Fetched origin/main · 1 ahead, 1 behind ⚠ Pull will conflict README.md both sides edited the intro · ~3 lines overlap Suggested Merge — keep both histories, resolve once [Enter] gitrust "pull" merge commit · resolve markers in README.md Other options [r] gitrust "rebase" replay your work on top · resolve per commit [f] gitrust "force push" ⚠ rewrites 1 remote commit · you own this branch [d] gitrust "discard mine" ⚠ drops 1 local commit · gitrust undo restores it for 30d [?] explain conflict markers [why] why these 4 [q] quit ▸
  • Demote the reasoning leak. Make the debug line dim, prefix it with dbg →, indent it under the command. Right now it floats between user input and result like it's part of the answer.
  • Replace "predicted" with the actual fact. Pull will conflict + status line (1 ahead, 1 behind) gives the user diagnostic context the original buried.
  • Tell them what's conflicting, not just where. "both sides edited the intro · ~3 lines overlap" tells them whether to even bother. Three lines is a 60-second fix; 300 lines is "find the other dev first."
  • Promote one option, demote the others. Cursor on Enter = Merge. Single-key shortcuts for the rest. The current "Do nothing — exit and decide later" default looks safe but trains people to bail.
  • All four options speak GiTrust. Not git pull --rebase, just gitrust "rebase". The literal git command can show on hover/expand for the curious.
  • Severity reflects branch reality. Force-push on your own branch is ⚠, not ⚠⚠. Save ⚠⚠ and ⛔ for cases where shared history actually breaks.
  • Recovery promise inline. "gitrust undo restores it for 30d" right next to the discard option.
  • Move the wall-of-text behind ?. Conflict-marker syntax tutorial: useful once, noise the other 99 times.

02Plan-preview box before execution

A boxed step list is right. The mistake is paraphrasing the steps ("Stage your changes, write a commit message, push to origin") instead of showing the literal command + the literal scope. Devs trust diffs and filenames, not English.

Typical wrap-in-English plan box
$ gitrust "push my login changes" Plan ┌─────────────────────────────────────────────────────────┐ │ 1. Stage your login-related changes │ │ 2. Create a commit with a generated message │ │ 3. Push the current branch to its remote ⚠ │ └─────────────────────────────────────────────────────────┘ Continue? [Y/n]
Concrete plan box
$ gitrust "push my login changes" Plan · on feat/session-refresh, 2 commits ahead of origin 1 add src/auth/login.rs +87 −12 src/auth/session.rs +new 2 other tracked files match "login" — skipped, press [a] to include 2 commit "Add session refresh + token rotation to login flow" generated · [e] edit message 3 push → origin/feat/session-refresh ⚠ first push of this branch · will create remote ref [Enter] run all [s N] skip step N [e N] edit step N [q] cancel ▸
  • Show diffs and paths, not paraphrases. A dev scanning +87 −12 on login.rs learns more in 200ms than they get from "Stage your login-related changes."
  • Surface the "almost matched" set. When the LLM filters files by relevance, tell the user what it left out and let them grab it with one key. The biggest beginner footgun in this flow is silently missing files.
  • Make the commit message obviously editable. Wrap it in quotes (visual cue: this is a string), put [e] edit right next to it, not in a generic Y/n at the bottom.
  • Per-step skip, not just all-or-nothing. "Y/n" treats a 3-step plan as atomic; [s 3] "stage and commit but don't push yet" is the actual mental model devs have.
  • Annotate steps with what makes them notable. "first push of this branch · will create remote ref" warns about a thing beginners hit (the --set-upstream dance) before it bites.

03Reset preview + type-to-confirm

The trick with destructive ops isn't more friction — it's better-targeted friction. Show what's lost with enough specificity that the user genuinely re-decides. And pick a type-to-confirm string that's memorable in context, not a random word.

Generic reset confirm
$ gitrust "reset 3 commits back hard" ⚠⚠ DESTRUCTIVE — this will discard commits and working tree changes. 3 commits will be lost. 2 files will revert. Recovery snapshot will be created. Type CONFIRM to proceed: ▸
Specific, recoverable
$ gitrust "reset 3 commits back hard" ⚠⚠ Hard reset · feat/session-refresh → HEAD~3 Commits dropped (3) a3f9c12 feat: session refresh ← HEAD, 12 min ago, you 8b21e44 wip: token plumbing 47 min ago, you c0d4a89 refactor: extract auth utils 2 hr ago, you Working tree reverts src/auth/login.rs −87 +12 (undoes today's work) src/auth/session.rs deleted (file goes away) ↻ Snapshot saved · gitrust undo → restores all of the above for 30 days Type the branch name (so you know what you're resetting): feat/session-refresh ▸
  • Show commits with author + age. "12 min ago, you" vs "2 days ago, alex" changes the decision. The original "3 commits will be lost" doesn't.
  • Annotate what each file change means in plain words. "undoes today's work" / "file goes away" — a beginner scanning −87 +12 alone won't internalize what's actually about to vanish.
  • Type-to-confirm = type the branch name, not the word CONFIRM. Typing CONFIRM is muscle memory after the second time. Typing feat/session-refresh forces eye contact with the thing you're modifying. (Same trick GitHub uses for repo deletion.)
  • Promise recovery in the same visual block as the loss. The green line and the red losses live together — the user sees the safety net at the same moment they see the cliff.
  • Skip "Recovery snapshot will be created." "Will be" is the wrong tense; take the snapshot first, then say "Snapshot saved." Removes a what-if.

04Detached-HEAD rescue

This is the single state where beginners are most likely to panic and the most likely to lose work. Never say "detached HEAD" first — that phrase is the source of the panic.

Jargon-first
$ gitrust status HEAD is detached at a3f9c12. You are in detached HEAD state. You can look around, make experimental changes and commit them, and you can discard any commits you make in this state without impacting any branches by switching back to a branch. Options: 1. Create a new branch from here: git switch -c <name> 2. Return to your previous branch: git switch - 3. Discard (if you have new commits, they'll be lost) >
Plain-English-first
$ gitrust status ⚠ You're not on a branch right now. You're looking at commit a3f9c12 directly (the tag v1.4.0). Reading code here is fine. Any new commits you make will be lost unless you save them to a branch first. What do you want to do? [Enter] Save my current spot as a new branch recommended name? explore-v1.4.0 (you can change it) [m] Go back to main you have no new commits here yet, safe [s] Stay here, I'm just reading [?] Why am I in this state? ▸
  • Lead with the consequence, not the term. "You're not on a branch" → "any new commits will be lost" is the causal chain a beginner needs. "Detached HEAD" is for the [?] explainer.
  • Detect "is this user about to lose anything?" first. If they have no new commits, going back to main is genuinely safe — say so. If they have 3 new commits, the safe-default option changes to "save as branch" and the "go back" option gets a ⚠.
  • Pre-fill the branch name. If they checked out tag v1.4.0, suggest explore-v1.4.0. If they checked out a SHA, use explore-a3f9c12. Beginners freeze on the "pick a name" step.
  • Anchor the SHA to something they recognize. "commit a3f9c12 (the tag v1.4.0)" or "(2 commits before main)" — beginners don't read SHAs as identities.

05Branch-name sanitization

Small flow, easy to over-engineer. The right answer: don't lecture, just suggest, and let Enter take the suggestion.

Lectures the user
$ gitrust "make a branch called feat/Login Page (v2)" Error: Invalid branch name. Git branch names cannot contain spaces, parentheses, or several other characters. They are also conventionally lowercase with hyphens. Please provide a valid branch name and try again.
Suggests and moves on
$ gitrust "make a branch called feat/Login Page (v2)" Git won't allow spaces or parens in branch names. Suggested feat/login-page-v2 or type your own: _ [Enter] use suggested [Esc] cancel
  • No "Error:". Nothing failed yet — GiTrust caught it before the failure. Use the saved keystrokes for a fix, not a scolding.
  • Don't enumerate every illegal character. Show the rule that mattered here ("spaces or parens"). The full rules go behind [?].
  • Make the suggestion typeable too. Cursor in the "type your own" field, pre-filled with the suggestion — backspace edits, Enter accepts. One state, not a binary.

06½Plan-execution box (commit flow)

New observation from the fuller loop. The current box has three small issues that compound: heavy double-line chrome, raw git commands inside a GiTrust box, and ⚠ on git add — which is fully reversible and shouldn't dilute the caution marker.

  • One ⚠, not two. git add is reversible (git reset). commit is the line where history changes. Marking both dilutes the meaning of the marker — it should mean "pay attention here," not "a write happens here."

  • End with the obvious next step. After a commit, the next thing 90% of users want is push. After a push, the next thing is a status check. Lead them. (And always mention gitrust undo within reach.)
  • Per-step skip on the plan. [s 2] = "stage but don't commit yet" turns a binary Y/n into the actual decisions devs make. Especially useful for the "oh wait, let me see the diff before committing" moment.

06Recovery snapshot listing

Snapshots are the marquee safety feature, but they're only valuable if a panicked user can find them in < 10 seconds. gitrust undo should be the muscle-memory command — and it should be discoverable from every destructive-op screen.

Reflog-flavored
$ gitrust snapshots Recovery snapshots: gitrust-snap-2026-05-27T13:04:22Z a3f9c12 HEAD~3 before reset gitrust-snap-2026-05-27T12:18:01Z e7c1a90 before push --force-with-lease gitrust-snap-2026-05-26T19:55:30Z 9bb2e44 before discard gitrust-snap-2026-05-24T10:02:11Z c0d4a89 pre-merge fix/auth → main Run gitrust restore <snapshot-name> to recover.
Designed for the panic moment
$ gitrust undo What would you like to undo? last 7 days, newest first [1] 2 min ago before reset --hard 3 commits, 2 files restoring will bring back: feat: session refresh + 2 more [2] 1 hr ago before force push 1 commit rewritten restoring will: revert origin/feat/login to the pre-force state [3] yesterday before discard mine 1 commit dropped [4] 3 days ago pre-merge fix/auth → main conflict-resolution state [a] show all (12 in last 30 days) [q] quit ▸
  • Rename the command. gitrust snapshots is for the future-you who's reading docs; gitrust undo is for the right-now-you who just made a mistake. Make both work, but lead with undo.
  • Relative timestamps, not ISO. "2 min ago" routes around the panic. ISO is for logs.
  • Describe what restoring will do, not what the snapshot is named. "restoring will bring back: feat: session refresh + 2 more" closes the loop the user is actually asking about.
  • Surface this entry point everywhere destructive. Every ⚠⚠ / ⛔ screen should mention gitrust undo by name. Discoverability is the feature.
  • Hide history past 7 days behind [a]. A 30-day list scrolls; a 7-day list fits.

07Proposal: render the plan as a timeline

Picking up the thread from 06½ — the ASCII ╔═╗ plan box conveys "these are steps" but loses the flow once execution starts. A vertical rail (in the spirit of terminal.css timeline) gives you a single visual that animates: nodes light up as steps complete, the currently-running step pulses, and what's done vs. pending is obvious at a glance.

The same component renders all three states below — plan preview, mid-execution, complete — with only the node modifiers changing. One mental model from drafting to receipt.

1 · Drafted awaiting confirm
$gitrust "commit my changes"
  • stage README.md +4 −1
    all matched files · reversible with gitrust "unstage"
  • commit "fix(README): add conflicting thing" ⚠
    generated from diff · [e] edit
  • push → origin/main ⚠
    your branch · 0 collaborators behind
Enter run all · e 2 edit message · s 3 skip push · q cancel
2 · Running step 2 of 3
$gitrust "commit my changes"
  • staged README.md +4 −1
    42 ms
  • commit… "fix(README): add conflicting thing"
    writing index → tree
  • push → origin/main ⚠
    queued
Ctrl-C abort · staged work preserved · snapshot @ aa44620 taken before run
3 · Done 3 of 3 ✓
$gitrust "commit my changes"
  • staged README.md +4 −1
  • committed "fix(README): add conflicting thing"
    aa44620 → 0de4a0d
  • pushed origin/main 1 commit
    origin/main now at 0de4a0d
Next: gitrust "status" · gitrust "log" · undo this commit with gitrust undo
  • One component, three states. Drafting / running / done all share the same vertical rail. The user learns the visual once and reuses it for every multi-step GiTrust command. ASCII boxes don't scale this way — they're inert once printed.
  • Status lives on the node, not in a separate column. Empty circle = pending, pulsing yellow = running, filled green check = done. Color + shape + motion = readable at a glance even when colorblind or in low-light terminals.
  • The card carries everything else. Verb (stage / commit / push), target, diff stat, severity marker, optional meta line. Same layout per step — no special-casing.
  • Severity tier drives marker placement on the card itself, not as a column. Caution ⚠ sits next to the verb. Destructive ⚠⚠ / irreversible ⛔ would tint the card border.
  • The footer changes meaning per state. Drafted → keymap. Running → abort safety. Done → next moves + undo. Same slot, different role — always actionable.
  • Cheap to render in a real TTY. Even though this is HTML, the underlying pattern is just box-drawing rail + step text + ANSI color. Rust crates like indicatif already do the pulsing-node animation. The visual maps directly to a real terminal; no React required.
  • Falls back gracefully. In non-TTY (CI logs, piped output), the timeline collapses to a numbered list with explicit prefixes ([done], [run], [pending]) — same information, no escape codes.

Better selection — the best picker is no picker

The arrow-key list works, but it forces the user to weigh options every time. A great agentic CLI uses everything it knows — branch context, repo conventions, the user's history — to make the right choice the default. The picker is the fallback for when prediction fails or the stakes are too high to auto-pick. Five patterns, roughly in order of preference:

P1Predict + confirm — turns 4-option pickers into 1-keystroke yes/no

GiTrust already knows: your branch (feat/session-refresh, solo), the repo's merge history (last 20 merges = 18 rebases), the size of the conflict (3 lines, one file). It can rank the four options itself and present one with a confirmation. The picker hides behind ?.

Current — flat picker
? Pick a resolution strategy: > Merge (creates a merge commit; you'll resolve markers) Rebase (replays your 1 commit(s) on top of remote) Force-push (with-lease) — keep YOUR version, overwrite remote ⚠⚠ Discard local — drop your 1 commit(s), take 1 from remote ⚠⚠ Do nothing — exit and decide later [↑↓ to move, enter to select, type to filter]
Predict + confirm
⚠ Pull will conflict on README.md (~3 lines) Suggested · Rebase (this repo uses rebase 18/20 times; you're solo on this branch) [Enter] do it gitrust "rebase" [m] merge instead creates a merge commit [?] all options incl. force-push, discard [q] back ▸
  • One keystroke for the right answer. Most resolutions don't need a menu — they need a smart default with a fast escape.
  • Show the reasoning for the suggestion in dim text. "this repo uses rebase 18/20 times; you're solo on this branch" turns a black-box pick into a teachable moment. Users learn the heuristic; juniors learn the convention of their team.
  • Promote the second-most-likely option to a single key. In this case [m] merge — the user can do the next-most-common thing in one keystroke without opening the menu.
  • Hide the long tail behind [?]. Force-push and discard aren't gone — they're one key away. But they don't crowd the safe path.
  • Falls back to the picker. If prediction confidence is low (new repo, weird state, conflicting signals), skip the suggestion and open the full picker. Mark which mode you're in subtly (Suggested vs Pick a strategy).

P2Outcome-first picker — show what the graph looks like, not what the command is

When the full picker IS needed (stakes too high, prediction unsure), reframe it around the resulting commit graph. Devs reason about graphs better than they reason about commands. ASCII art is cheap and renders in every terminal.

Outcome-first picker
How should the histories combine? your branch · feat/session-refresh [a] Merge ●─●─● main keeps both histories ╲ ╲ ●───◆ (merge commit) [b] Rebase ●─●─●─●─● main linear · your work on top your commit, replayed [c] Force-push ●─●─● main ⚠⚠ rewrites origin ✗ remote commit deleted [d] Discard mine ●─●─● origin/main ⚠⚠ takes remote as-is ✗ your local commit deleted [Tab] preview files affected · [Enter] pick · [?] explain a choice ▸
  • End-state, not command. Devs ask "what will my graph look like after?" The picker should answer that, not list verbs.
  • Severity is rendered as deletion in the graph. ✗ remote commit deleted under Force-push is a more visceral warning than the abstract ⚠⚠ marker alone.
  • Direct-key shortcuts. [a] [b] [c] [d] beats arrow keys — single keystroke, screen-reader-friendly, indexable in muscle memory.
  • Tab = preview, Enter = pick. Separating "explore" from "commit" is the single biggest accessibility win. Currently the cursor IS the decision — there's no way to look without picking.

P3Inline expand — accordion for when descriptions need to be deep

A middle ground: list stays compact, but pressing → or space expands the current option to show full detail (commands, files affected, recovery path). Enter commits. Works because most users only need detail on the option they're hovering — not all four at once.

  • Two-tier disclosure. Skim the list. Stop at an option. Hit space. See everything about it. Skim or commit. The current picker forces you to read all four descriptions every time, even when you already know you want Merge.
  • Detail block has a fixed shape — Runs / Affects / Result / If it goes wrong. Same four lines per option means the user learns where to look and doesn't have to re-parse the layout per choice.
  • Recovery path is part of the detail, not separate. By the time you've expanded a destructive option, you've seen gitrust undo next to it.

P4Wizard mode — decompose the choice into yes/no questions (beginner opt-in)

For users who genuinely don't know which strategy to pick, the choice is unfamiliar because the trade-offs are unfamiliar. A short Q&A maps to a strategy without forcing the user to learn jargon first. Off by default for power users; opt-in via gitrust config verbosity beginner or first-run questionnaire.

Wizard mode
⚠ Pull will conflict. Two questions to figure out the right move: 1. Is anyone else committing to main right now? [y] yes, others are working here [n] no, it's just me (default · based on last 30d of commits) ▸ n 2. Do you want the merge to show up as a separate event in history? [y] yes, preserve it as a merge commit [n] no, keep history linear (default · this repo prefers linear) ▸ n → Rebase fits. [Enter] do it · [?] show me the other options anyway
  • Questions are about intent, not implementation. "Do you want the merge as a separate event" is a question a non-git-expert can answer. "Merge or rebase?" is not.
  • Each question has a smart default. GiTrust can guess the answer to "is anyone else on this branch" by checking recent commit authors. The user just confirms.
  • Two questions max. A wizard with 5+ steps is a survey. A wizard with 2 binary steps maps perfectly to 4 strategies.
  • Always offer the escape hatch. "[?] show me the other options anyway" lets the user override the wizard's conclusion without restarting.
  • Off by default; tied to verbosity. Senior devs get the predict+confirm flow (P1). Beginners get the wizard. Same GiTrust binary; different mode.

P5File multi-select — group by confidence, not relevance

The other selection flow in GiTrust. "File multi-select grouped by relevance" is right; the unlock is being explicit about how confident the LLM is per file, and letting the user toggle groups, not just files.

Bucketed file picker
$ gitrust "commit my login changes" Select files to stage · matched on "login" · 4 of 12 changed files selected ▼ Related (3 · pre-checked) [1] toggle group [x] src/auth/login.rs +87 −12 named in query [x] src/auth/session.rs +new imports login::* [x] tests/login_test.rs +34 covers login.rs ▼ Uncertain (2 · visible, not pre-checked) [2] [x] src/db/users.rs +4 −2 touched in same edit session [ ] README.md +12 −3 mentions "login" in changelog ▶ Unrelated (7 · hidden · [a] to show) Total: 4 files · +125 −12 · about 1 commit's worth [space] toggle file [1-2] toggle group [a] show skipped [n] none [Enter] stage
  • Three buckets matching the real classifier output. GiTrust's two-pass resolver already emits { related, uncertain, unrelated } with a per-file reason line. Use the existing struct names: Related (pre-checked) / Uncertain (visible, not pre-checked) / Unrelated (hidden). No new classification work needed — just surface what's there.
  • Show the per-file reason inline. The classifier already produces "named in query," "imports login::*," "touched in same edit session." Right now it's only visible with --show-all; lift it into the picker as a dim trailing note. This is the cheapest single fix in the doc.
  • Promote --show-all to a keystroke. Today it's a flag (long, requires re-running). [a] show skipped reveals the Unrelated bucket inline. The 1-in-8 under-inclusion rate the model hits becomes a 1-keystroke recovery instead of a re-invocation.
  • Toggle a whole bucket with one key. [1] / [2] = include or exclude the whole group. Beats space-bar-marching through 5 files.
  • Collapsed by default for the Unrelated bucket. The classifier is right ~88% of the time on this group; don't waste vertical space until the user asks.
  • Running total of scope. "4 files · +125 −12 · about 1 commit's worth" closes the loop on "did I include too much / too little." Updates live as the user toggles.

Not one selection UX — a layered system. GiTrust picks the right one based on confidence, stakes, and user verbosity setting.

Designing around the model

qwen2.5:3b on a laptop CPU has hard limits. They aren't problems to hide — they're design inputs that should shape the UX. Eight patterns that exist because of how the model behaves. Several of these supersede or refine recommendations I made earlier.

M1 · Engine indicator

Show which engine answered — fast-path or LLM

60% of queries hit the canonical fast-path (~25 phrases, 100% reliable, instant). 40% go through the LLM (~92% accurate, 400ms–2s). Same output surface, completely different reliability. A single glyph tells the user which they're getting.

$ gitrust "push"
  ⚡ pushed origin/main · 0de4a0d → 1a3f4b8       (fast-path · 12ms)

$ gitrust "ship my login work to prod"
  ◉ understanding…                              (llm · ~1s)

Power-user behavior emerges from transparency — once users see the ⚡ on certain phrasings, they reach for them naturally.

M2 · No streaming

Stage labels replace token-streaming reasoning

Supersedes recommendation F. Since the LLM response isn't streamed, surface stages of the pipeline with their typical latency budgets. Users learn the rhythm; a stalled stage is the user's cue to Ctrl-C with confidence.

  ✓ intent: commit       820ms (budget ~1s)
  ✓ files: 3 selected    640ms (budget ~700ms)
  ⠋ message: drafting…   ~400ms
M3 · NeedsClarification (3% of queries)

Treat low-confidence as a first-class state, not an error

The classifier itself signals when it's unsure. Today GiTrust surfaces an editable prompt; the upgrade is to also offer GiTrust's best 2–3 guesses as one-key picks so the user doesn't have to retype.

$ gitrust "the auth thing"
  ◉ not sure what you want. My best guesses:
    [a]  commit your auth changes        5 modified files in src/auth/
    [b]  switch to branch feat/oauth     last touched 12m ago
    [c]  show recent auth commits

  ▸ or refine: the auth thing _
M4 · AmbiguousFeature (5% of queries)

Reuse the P5 picker — items are matches, not files

The resolver returns multiple plausible interpretations of "auth." Same bucketed-picker pattern as the file selector; the rows are now matched features with the type baked into the row.

$ gitrust "commit the auth thing"
  ◉ 3 things match "auth" in this repo:
    [1]  files ·    src/auth/* + tests/auth_test.rs    5 files, +120
    [2]  branch ·   feat/oauth-refresh                  2 ahead
    [3]  recent ·  auth_middleware.rs                  you, 12m ago

  [Enter] pick highlighted  ·  [r] refine query
M5 · TooManyFiles gate (>50 modified)

Don't refuse — narrow

A flat refusal is correct (the model truncates silently past 50 files) but a refusal that helps the user narrow turns a dead-end into a one-key recovery.

$ gitrust "commit everything"
  ⚠ 87 modified files — too many to reason about safely.

  Narrow by:
    [1]  recent edits (last hour)    32 files
    [2]  current directory            14 files
    [3]  type a hint to filter        e.g. "login", "tests"
    [a]  proceed anyway · group by dir  ⚠
    [q]  cancel
M6 · Closed operation set

The LLM never invents a command — lean into that in onboarding

Because the classifier picks from a fixed ~25-op enum (not free-text), there's no "the AI made up a destructive command" failure mode in GiTrust. That's a trust statement worth saying out loud in gitrust help or first-run copy: "GiTrust always picks from a known list of ~25 git operations. It will never invent a command." Differentiates GiTrust from cloud LLM CLI wrappers where this fear is legitimate.

M7 · Reasoning lines are Rust, not LLM

Trust the dim "why" text completely — it can't hallucinate

Clarification for P1 and elsewhere: when I wrote "this repo uses rebase 18/20 times; you're solo on this branch," that's a Rust-computed line over real git data, not LLM output. The danger classifier, recovery choice, refname validation, and severity tier are all pure Rust. The LLM is never trusted with safety-critical text. Worth surfacing in copy: "GiTrust's reasoning lines are computed from your actual repo — the AI never writes warnings."

M8 · Corrections extend the fast-path

"Remember this" isn't fine-tuning — it's growing the canonical list

Refines recommendation A. The misclassification correction shouldn't try to retrain qwen. It should write to a per-repo aliases file that's consulted before the LLM, as part of the fast-path. Three corrections on the same phrasing make it a 100%-reliable instant response — effectively turning each user's repo into a tuned dialect.

$ cat .git/gitrust/aliases.toml
[aliases]
"changes today"        = { op = "log", since = "1d" }
"my work-in-progress"  = { op = "diff", scope = "uncommitted" }
"ship to staging"      = { op = "push", target = "staging" }

# Aliases are checked before the LLM. Edit by hand or via:
#   gitrust alias "<phrasing>" → <op>

Bonus: the aliases file is human-readable + diffable. Teams can commit it to share GiTrust dialect across collaborators.

More to consider — things I didn't cover in v1

Re-reading the brief and the screenshots, here are the bigger structural questions worth a pass. Most are not visual issues, but they shape the visual surface.

A · Misclassification

What happens when the LLM picks the wrong intent?

The classifier hits ~92% intent accuracy on the 40% of queries that reach it (60% bypass via fast-path). So ~3% of all queries land wrong. Today the debug reasoning line is honest but read-only — there's no in-place fix.

$ gitrust "show me my changes"
  ↳ ran log -p HEAD~5    [w]rong? · [d]iff instead · [s]tatus instead

[output…]

→ If wrong, this phrasing becomes a fast-path alias for next time.

The correction doesn't fine-tune qwen — it extends the canonical fast-path list (per-repo .git/gitrust/aliases.toml). Three corrections turn a frequently-wrong phrasing into a 100%-reliable instant response. See M8 for the file format.

B · REPL state

The REPL needs a persistent "focus" line

One-shot CLI is stateless; the REPL isn't. After 5 commands the user has built mental context ("I'm working on session-refresh, I have 2 untracked files, I haven't pushed in 20 min"). Surface a one-line status header at every prompt:

[main↑1↓2 · staged: 1 · last push: 23m]
gitrust> _

No retyping status every other command. Stale ahead/behind counts update lazily.

C · Scriptability

Auto-detect TTY, drop chrome when piped

The picker, box drawing, color, animation — all great in a real terminal, all garbage in gitrust "status" | grep ahead or in CI logs. Detect isatty(stdout) and switch to a parseable mode. Optional --json for tooling.

$ gitrust "status" --json | jq .ahead
1

A CLI that works in scripts is a CLI that gets adopted by teams, not just individuals.

D · First run

Where does a brand-new user learn what GiTrust can do?

GiTrust's superpower is natural language — but that's only valuable if users know to try things. A 30-second first-run tour beats a 30-page README.

$ gitrust
✓ GiTrust ready · ollama up · qwen2.5:3b loaded

First time? Try any of these:
  gitrust "what changed today"
  gitrust "commit my work-in-progress"
  gitrust "am I behind on main"

Or just describe what you want. Type help to see the menu.
gitrust> _
E · Progressive disclosure

The 5th-commit user and the 500th-commit user need different scaffolding

The "Manual fix needed: edit each file, remove markers, then git add…" block is gold for a beginner and noise for a senior. Track a per-user counter; collapse hand-holding behind [?] after N successful resolutions of the same op. Show a setting in gitrust config so it's auditable.

verbosity: auto (beginner)  · force with --verbose / --terse
  show-recovery-hint:   always
  show-conflict-syntax: until 5 successful resolutions  ✓ 4 / 5
  show-reasoning:       on GITRUST_DEBUG=1
F · Latency

No streaming → surface the stage, not the partial response

Ollama's format: json mode waits for the full response, so streaming the LLM's prose isn't an option. Instead, show which stage of the pipeline GiTrust is in, with each stage's typical latency budget. Users learn the rhythm and can Ctrl-C deliberately when something stalls.

$ gitrust "ship my login work to prod"
  ⠋ understanding intent…       ~1s
  ✓ matched intent: push
  ⠋ matching files (12 changed) ~700ms
  ✓ 3 files selected
  ⠋ rendering plan…

If a stage exceeds its budget by 2×, dim the spinner and offer an explanation + Ctrl-C with a graceful out. The 60% of queries that hit fast-path get no spinner at all — just a tiny ⚡ glyph to confirm "instant." See M1 + M2.

G · Conventional commits

Detect convention before applying it

GiTrust drafted fix(README): add conflicting thing — nice if the repo uses conventional commits, surprising if it doesn't (some repos prefer README: add… or Add conflicting thing to README). Scan the last 20 commits; match the dominant style. Cache per-repo in .git/gitrust/style.

H · Cross-platform

Plan for cmd.exe and Powershell, not just iTerm

Unicode markers (⚠⚠ ⛔), the rich picker, box-drawing characters, ANSI color — all conditionally available across Windows terminals, screen-readers, and SSH sessions where TERM is degraded. Test the degraded path explicitly; don't let a Windows beginner see ??Ó instead of ⚠⚠ the first time they hit a destructive op.

marker tier
  safe         (no marker)         (no marker)
  caution      ⚠            ASCII: !
  destructive  ⚠⚠           ASCII: !!
  irreversible ⛔            ASCII: XX

Q4 · Inquire picker bug ✓ identified

Pin .with_starting_cursor(0) explicitly

The "Do nothing highlighted" behavior in the original screenshot is inquire::Select restoring last-selection. Two-line fix at the call site for every picker: pin starting cursor to index 0, and put your safest option at index 0 (already the case for the conflict picker).

Belt-and-suspenders: if you ever do want last-selection memory (e.g. for an option that's tied to user preference, not safety), do it explicitly per-call site — not as the default behavior.

Q5 · Severity-by-context ✓ tiered

Cheap signals always; ls-remote only at force-push confirm

Tiered cost ladder:

  • Free (every classification): branch-name match (main/master/develop/trunk) → upgrade marker on protected branch names. Catches ~80% of correct ⛔ calls.
  • Cheap-ish (~50ms, before destructive ops): walk last N commits, count authors that aren't user.email → real "3 collaborators behind" instead of the lying behind > 0 heuristic. Fix has_foreign_commits() to do this.
  • Expensive (200–500ms, gated behind force-push confirm only): git ls-remote to verify the remote tip hasn't moved since last fetch. Pay the latency once, where it matters.
  • Skip: GitHub branch protection API — host-specific, doesn't belong in a host-agnostic tool.
